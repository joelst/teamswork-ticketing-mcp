# Security model

## Assets and trust boundaries

- **Ticketing API key**: grants full read/write access to the Ticketing instance. Stored only in Azure Key Vault
  (`Ticketing--ApiKey`, purge protection on). The container app reads it through a Key Vault secret reference with a
  user-assigned managed identity (`Key Vault Secrets User`). Locally: user secrets or Key Vault via
  `DefaultAzureCredential`. It is appended to the outbound query string inside `TicketingClient` only; the default
  HttpClient logger (which prints full URLs) is removed, exceptions never carry the URL, and tests assert the key
  never appears in error text.
- **Ticket data** (names, emails, descriptions): only flows to authenticated, assigned callers and is never logged.
  Logs contain method, path, status, and timing.
- **Caller identity**: Entra ID access tokens for audience `api://<clientId>`.

## Controls

| Area | Control |
| --- | --- |
| Authentication | Microsoft.Identity.Web validates issuer (single tenant), audience, lifetime, and signature against Entra keys. Tokens with neither `scp` nor `roles` are rejected. Startup refuses `Entra:TenantId` values of `common`, `organizations`, or `consumers`, which would accept tokens from any tenant. |
| Authorization | Policy `McpCaller`: `scp` contains `access_as_user` **or** `roles` contains `Ticketing.ReadWrite`. Service principal has *assignment required*, so unassigned users cannot even obtain a token. |
| Discovery | RFC 9728 protected-resource metadata and `WWW-Authenticate` challenge, so clients learn the authorization server without guessing; no anonymous MCP endpoint. |
| Actor integrity | Acting user comes from token claims (or the configured service account for app-only tokens). No tool accepts a `user` argument; the integration test asserts this for every tool. |
| Transport | Stateless Streamable HTTP: no server sessions, nothing to hijack, horizontal scaling safe. HTTPS-only ingress (`allowInsecure: false`); TLS terminated by Container Apps. |
| Input validation | Every tool validates arguments before they reach the upstream URL/body: UUIDs, enums, `YYYY-MM-DD` dates, datetime filters, page-size caps, text length caps, list caps (50 tags, 100 custom fields, 20 links), URL schemes (http/https only) for links. People, tags, and custom fields given by name are resolved against the instance's own lists (cached). Every person value (assignee, requestor, people-picker fields) goes through one rule: an ID (compared as an object ID, in any GUID form) or email that belongs to someone in the assignee list must match that person in full, someone outside the list can't use a listed person's name (compared after removing invisible characters and accents (precomposed or combining, on Latin, Greek and Cyrillic letters) and mapping everything that displays as plain Latin letters to them, using tables generated from Unicode data by `scripts/gen-name-tables.py`: the NFKC compatibility forms and the UTS #39 confusables whose prototype is Latin, plus small capitals; spacing and case are ignored), can't have invisible characters in their name (except the zero-width joiner and non-joiner that Persian and Indic names use), and must have an all-ASCII email, so a look-alike letter can't imitate a listed address; an outsider's ID must be a standard object ID or their email (sent in standard form), and an assignee must be on the list (an empty or unreadable list refuses all assignees). Look-alikes between non-Latin scripts aren't mapped. An email must be one plain address with an ASCII DNS domain name (punycode for an internationalised one): lists and display-name forms, where the address checked would differ from the text sent, are refused, and so are Unicode domains, since folding them depends on globalisation data the Linux build doesn't carry, and IP-address domains. None of these checks depend on that data, and CI runs the tests without it too. People outside the list are accepted as given for requestors and people fields, because the server has no directory to check them against; `Ticketing:ExternalEmailDomains` limits them to named domains, which stops text an agent has read from making an outside address a ticket's requestor (and so the recipient of its notifications). Custom field values are checked against each field's type and options (dates as `YYYY-MM-DD`, list options by key, people resolved), and fields of a type or option shape the server can't check are refused. Path IDs such as `activityId` are limited to letters, digits, `-` and `_`, so `..` can't navigate the upstream path. Continuation tokens must be visible ASCII, because they are sent as an HTTP header and the .NET HTTP stack writes such values to the wire unchecked (a CR/LF would inject headers into a request that carries the API key); the client re-checks every header value. |
| HTML from agents | `descriptionHtml` and `commentHtml` are sanitised with HtmlSanitizer before they are sent, keeping formatting, headings, lists, tables, quotes, code, and http(s) links. Removed: script, event handlers, frames, and non-http(s) URLs (HtmlSanitizer's defaults), plus form controls (credential-phishing forms), `style` (full-screen overlays, `url()` beacons), images and image maps (zero-click beacons that could carry data the agent read), `name` (DOM clobbering), and `target` (reverse tabnabbing). Agents can be steered by text they read, so this doesn't rely on the vendor's own sanitising. |
| Error disclosure | Only messages written for the agent (validation, upstream API errors, identity problems) reach the client. Any other exception is left to the MCP SDK, which logs it and returns a generic error, so type names, configuration, and library messages never leak. |
| Rate limiting | Per caller: 60 MCP requests a minute by default (`Mcp:RequestsPerMinutePerCaller`), keyed by the token's tenant and object ID, answered with 429 and `Retry-After`. Because one tool call can make several upstream requests, each caller is also charged for every upstream request it causes, its retries included (`Ticketing:MaxUpstreamRequestsPerCallerPerMinute`, default 50 of the vendor's 100), and refused at once when its share is used, so one runaway agent can't use up the quota every caller shares. A request without an identified caller is charged to one shared key rather than going unlimited. The caller who starts a read of the shared instance cache is charged for it (and refused alone if their share is used up); callers who join that read aren't charged and never see another caller's quota error. That read's own retries (at most two) count only against the process-wide limit. Callers using one app-only identity (such as a Foundry managed identity) share that identity's share. The shared instance cache can't be emptied or re-read at will: a copy is replaced only after a successful read, concurrent readers share one read, and a refresh is honoured at most once every 30 seconds for the whole cache (not per time zone offset, so cycling offsets doesn't multiply it); the slot is taken when the refresh starts, so concurrent refreshes at different offsets don't each go out. Upstream: a process-wide sliding window matching the vendor's 100 requests / 60 s, bounded retries with backoff on 429/5xx, and at most `Ticketing:MaxConcurrentUpstreamRequests` (8) requests in flight at once, so the responses held in memory are bounded (each up to 8 MiB); more than 32 waiting are refused. An HTTP-200 error response is recognised from its `error` and `message` fields alone, without a second full parse. |
| Resource limits | Tools that filter in the server (`list_my_tickets`, `list_sla_risk`, `count_tickets`) and `find_ticket_by_number` read at most `Ticketing:MaxScanTickets` tickets (default 1000) per call; each ticket-number page is charged at least 50, so empty pages can't make it loop (at most 21 requests by default). `find_similar_tickets` makes at most four requests. Scans keep only a summary of each match, so a scan of full tickets holds one page at a time. Request bodies over 1 MiB (`Mcp:MaxRequestBodyBytes`) get 413, in Kestrel and on `/mcp`. Upstream responses over 8 MiB (`Ticketing:MaxResponseBytes`) are refused, and `Ticketing:RequestTimeoutSeconds` bounds the whole upstream call including the body read (HttpClient's own timeout stops when the headers arrive). |
| Container | `mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled-extra`: distroless-style, non-root `app` user, no shell/package manager. The `-extra` variant adds the time zone data the server needs (and ICU, unused). Diagnostics disabled. 0.25 vCPU / 0.5 GiB. |
| Registry / pulls | ACR admin user disabled; the container app pulls with its managed identity (`AcrPull`). |
| Pipeline | Workload-identity-federation service connection (no stored cloud secrets). Pull-request builds get neither the service connection nor the production variable group: only the main-branch deploy stages use them (add branch-control checks on both so edited YAML can't reach them), and Bicep is linted without signing in. Packages, transitive ones included, are pinned by committed `packages.lock.json` files and restored in locked mode. `NuGetAudit` fails restore on known vulnerable packages (level *low*, warnings as errors). Image built by the .NET SDK, no Docker socket. Deploy stage guarded by an environment approval. |
| Supply chain | GitHub Actions are pinned to commit SHAs, because the release workflow holds `id-token: write` and the code-signing identity and a moved tag would run new code with them. Dependabot proposes NuGet and Actions updates weekly. |
| Key Vault | RBAC authorization, soft delete 90 days, purge protection. |
| Logging | Log Analytics with a 1 GB/day cap and 30-day retention; HttpClient URL logging removed. |
| Health | Separate anonymous `/healthz` for probes; the MCP endpoint is never probed. |
| File uploads | `upload_ticket_files` exists only over stdio, and only when `Ticketing:UploadRoot` names a folder. At startup the folder's real location (links resolved, names as stored) is checked: a drive root; a folder containing the home folder, the application data or configuration folders, or the user-secrets file; or a folder inside an application settings folder (AppData, `~/.config`) or a hidden folder in the home folder (`~/.ssh`) is refused, since client configurations there can hold the API key. The checks run on the canonical path and, on Windows, on the path the operating system reports for a handle to the folder, so a `subst` drive can't alias a protected folder; a folder Windows resolves to a network path (a share, `\\localhost\C$`, or a mapped drive) is refused, since it can't be compared with local folders. On Windows, a folder inside Windows' own temporary folder (at its fixed place, whatever TEMP says) is allowed; the temporary folder itself is refused. On Linux a folder under `/proc`, `/sys`, `/dev`, or `/run` is refused: those pseudo-filesystems expose process environments (`/proc/<pid>/environ` holds the API key) as regular files. Each path must resolve inside the folder, compared exactly, and each segment must name an entry exactly as stored, so a different spelling or an 8.3 short name (`ENV~1` for `.env`) finds nothing; no segment may be hidden (dot), a symbolic link or junction, or use wildcard or alternate-stream (`:`) syntax. Each file is opened and then the open file itself is checked: its real path as the operating system reports it for the handle (`GetFinalPathNameByHandle` on Windows, `/proc/self/fd` on Linux) must be inside the folder, and it must be a regular file with a single name, so a hard link to a file elsewhere is refused. On Linux the file is opened without waiting and without following a final link (`O_NONBLOCK | O_NOFOLLOW`), so a FIFO, or a path swapped for one after it was checked, can't hang the call, and the open handle is checked with `statx`, requiring the kernel to report the fields checked. Anything that can't be checked is refused. It is read from that handle, with the size limit enforced on the bytes read (at most 10 files and `Ticketing:MaxUploadBytes`, 10 MiB). Uploads are offered only on Windows and Linux; on macOS the tool isn't registered. The tool is annotated open-world, since it sends local data to a third party, and uploads are private by default. This limits what `upload_ticket_files` will read; it doesn't stop an agent that also has shell or file tools from copying a file into the folder first, so keep the folder out of reach of such tools or review uploads. |
| Local modes | stdio and `--local` HTTP run without authentication for developer machines only: `--local` binds to `127.0.0.1` regardless of `ASPNETCORE_URLS`, a middleware rejects non-loopback remote addresses, `Ticketing:ServiceAccount` is mandatory so every write has an explicit, operator-chosen actor, and startup is refused when `CONTAINER_APP_NAME` is present. Settings are read from the application's own folder, environment variables, user secrets, and the command line, never from the working directory, which MCP clients set to the user's workspace: a settings file planted there (by a cloned repository or an agent) could otherwise send every request, API key included, to another host or turn on uploads. The Bicep/pipeline never set `Auth:Mode`. |

## Residual risks and options

- **Upload folder contents**: anything placed in the upload folder can be uploaded, so keep it for files you mean to
  send, and away from agents that have shell or file-writing tools (they could copy a file into it first). Hard links,
  FIFOs, and devices are refused on Windows and Linux; uploads aren't offered on macOS, where the open file can't be
  identified without architecture-specific system calls.

- **Public ingress**: the endpoint is reachable from the internet but only Entra-authenticated, assigned callers can
  use it. For a stricter posture, add Container Apps IP restrictions (Foundry/Power Platform egress ranges) or move
  the app to an internal environment on a VNet and use Foundry's private MCP support.
- **Forwarded headers**: the app honours `X-Forwarded-For` and `X-Forwarded-Proto` from the Container Apps ingress
  (the only network path to the container), but not `X-Forwarded-Host`, which any client could set to choose the
  resource URL in the protected-resource metadata. Setting `Entra:PublicBaseUrl` pins that URL entirely. If you ever
  expose the container differently, restrict `KnownNetworks`.
- **Prompt injection**: ticket titles, descriptions, and comments are written by people, so text returned to an agent
  is untrusted input to it. The server can't prevent an agent from following instructions it reads; the controls
  above limit what a misled agent can do (no impersonation, sanitised HTML, per-caller limits).
- **Service-account attribution**: writes made with app-only tokens are attributed to one identity. Prefer identity
  passthrough where per-user accountability matters.
- **Vendor API key scope**: the key is instance-wide; rotate it in Key Vault (`Set-TicketingApiKey.ps1`) and restart the
  revision if it is ever exposed.
- **Optional hardening**: Container Apps built-in authentication (Easy Auth) can be layered in front of the app as
  defense in depth; keep in-app validation as the primary control so MCP discovery keeps working.
